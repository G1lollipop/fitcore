# FitCore 项目现状分析（MLE 视角）

> 读者：本项目作者，目标是把 FitCore 写进简历、申请美国 MLE（Machine Learning Engineer）实习。
> 本文用「招聘官 / 资深 MLE 面试官」的眼光，客观盘点这个项目**现在到底做了什么、哪些是真正的 ML 工程含量、哪些只是应用开发、还差什么**。
> 配套文档：[`02-后续开发计划.md`](./02-后续开发计划.md)、[`03-MLE学习指南.md`](./03-MLE学习指南.md)、[`04-简历与面试.md`](./04-简历与面试.md)。

---

## 0. 一句话结论

FitCore **已经不是一个普通的 "调用 LLM API 的 CRUD app"**。它内部有一套**可复现、metrics 驱动、带 CI 回归门禁的 RAG 检索评估体系**——这正是区分「会用 ChatGPT API 的前端」和「会做 ML 工程决策的 MLE」的关键。

但它目前的「ML 含量」**集中在检索（retrieval）与评估（evaluation）两块**，其余 AI 能力（对话 Agent、视觉识别、自然语言记录）本质上是**对 Gemini API 的编排（orchestration）**，缺少：
1. **自己训练 / 微调的模型**（目前 0 个，全是调用托管 API）；
2. **Agent / 生成层的系统化评估**（检索层评估很扎实，但 Agent 工具选择、答案忠实度没有 golden set）；
3. **线上可观测性与成本/延迟分析**（有 debug 字段，但没有结构化日志和 dashboard）。

> **战略判断**：现状足以支撑一条**很强的简历主线（RAG + Evaluation + MLOps）**。要让它从「不错」变成「让面试官眼前一亮」，下一步最高性价比的不是再加功能，而是 ①给 Agent/生成层补评估闭环，②加入至少一个**自己训练/微调的模型**来证明你不只是 API 调用者。具体见开发计划。

## 1. 项目是什么

FitCore 是一个 **AI 驱动的健身教练 web 应用**，monorepo，两个相互独立的子服务：

| 子项目 | 技术栈 | 职责 |
|--------|--------|------|
| `web/` | Next.js 16 (App Router) + React 19 + TypeScript + Supabase | 前端单页应用 + AI 编排层（对话 Agent、视觉、NLP 记录）+ 业务数据 CRUD |
| `rag/` | Python 3.11 + FastAPI + LangChain 1.x + Gemini | 独立的 RAG **检索服务** + 完整的离线/在线评估体系 |

核心交互链路（来自 `README.md` / `DEVELOPMENT.md`）：

```
浏览器
  ├── Server Actions ───────────────► Supabase（日志/计划/统计 CRUD）
  └── POST /api/ai/chat (SSE) ──► Next 服务端 Agent (web/lib/ai/agent.ts)
         ├── Gemini（对话 / 工具调用 / 视觉 / embedding）
         ├── Supabase（用户上下文、聊天记录）
         └── POST /v1/retrieve ──► FastAPI RAG 服务 (rag/)
                                     ├── 向量检索 + BM25 融合
                                     ├── 可选 CrossEncoder 重排
                                     └── 自适应 topK
```

一个值得注意的**架构决策**（面试可讲）：**检索与生成分离**。Python 服务只做「检索」（`/v1/retrieve`，不调 LLM），生成在 Next.js 的 Agent 里完成。这让检索层可以被独立评估、独立部署、独立扩展，是一个干净的边界。

## 2. 项目里的 5 个 AI/ML 能力面（逐个体检）

### 2.1 Tool-Calling RAG Agent（对话教练）

**文件**：`web/lib/ai/agent.ts`、`web/app/api/ai/chat/route.ts`、`web/lib/ai/rag-client.ts`、`web/lib/ai/user-context.ts`

**做了什么**：用 OpenAI function-calling 风格实现了一个 **2 步、3 工具的 Agent**：

- **Step 1 规划（非流式，`temperature=0.2`，`max_tokens=300`）**：LLM 看到用户消息 + 工具列表，一次性输出要调用哪些工具。
- **Step 2 工具执行（并行 `Promise.all`）**：
  - `set_retrieval_params`：LLM 自己决定召回数量 `k ∈ {3,5,8}`（简单问题 3、复杂问题 8），不发网络请求；
  - `query_knowledge_base`：POST 到 `/v1/retrieve` 拿知识片段；
  - `get_user_stats`：把已预取的用户上下文（profile / 目标 / 今日摄入 / 最近 5 条日志）格式化。
- **Step 3 生成（流式，`temperature=0.7`，`max_tokens=900`）**：把工具结果拼进消息历史，流式生成最终回答，通过 SSE 推给前端。

**亮点（可写简历）**：
- 用 **LLM 自主决定检索深度**（`set_retrieval_params`），而不是写死规则——这是「让模型做决策」的体现，比硬编码的 if-else intent 分类更先进（代码注释里明确说替换掉了旧的关键词 intent 分类器）。
- **会话模式后验分类**：根据用到哪些工具，把这轮标记为 `knowledge` / `personal` / `hybrid` / `direct`，并通过 SSE `done` 事件回传 `toolsUsed / retrievalK / mode / latencyMs` 等可观测字段。

**短板（面试官会追问）**：
- **没有任何评估**。Agent 的工具选择对不对、该检索时是否真的检索了、答案是否忠实于检索内容——目前全靠人工观感，没有 golden set、没有指标。这是当前**最大的、最容易补的 MLE 缺口**。
- 用户上下文格式化函数 `formatUserContext` 是**中文写死**的，即使英文对话也输出中文标签——细节瑕疵。
- `topK: 0` 作为「让后端自动判断」的信号，语义不透明。
- 记忆只有 10 轮滑动窗口，无摘要 / 长期记忆。

### 2.2 混合检索系统（Hybrid Retrieval）— ⭐ 项目最硬的 ML 部分

**文件**：`rag/app/services/rag_service.py`、`rag/app/services/retrieval/{chroma_store,supabase_store,compression,adaptive_k}.py`、`rag/app/infra/embeddings.py`、`rag/app/core/settings.py`

**做了什么**（这是真正有 ML 工程含量的部分）：

| 组件 | 实现 | 关键参数 |
|------|------|----------|
| **Embedding** | Gemini `gemini-embedding-001`，用 **Matryoshka 截断**到 768 维（`output_dimensionality`） | `EMBEDDING_DIM=768`，须与 Supabase `vector(768)` 一致 |
| **向量检索** | Chroma 相似度 / Supabase pgvector RPC（cosine `<=>`，HNSW 索引） | 召回 `k=10`（留重排空间） |
| **稀疏检索** | `rank-bm25`，全量语料载入内存 | `k=10` |
| **融合** | LangChain `EnsembleRetriever`（加权 RRF） | 权重 `RETRIEVAL_VECTOR_WEIGHT` 可配，默认 0.5/0.5，生产 **0.8** |
| **重排（可选）** | `HuggingFaceCrossEncoder` + `CrossEncoderReranker`（如 BGE reranker） | `RERANKER_ENABLED`，`top_n=10`；云端强制关闭 |
| **自适应 topK** | 纯字符串启发式（无额外 LLM 调用），按 query 复杂度返回 3/5/8 | `adaptive_k.py` |

**亮点（强简历素材）**：
- **真正的 hybrid retrieval**：向量（语义）+ BM25（词法）融合，且**融合权重是数据驱动调出来的**（见下方评估发现），不是拍脑袋。
- **双向量后端**（Chroma 本地 / Supabase pgvector 云端），同一套检索逻辑，工厂模式切换。
- **重排的优雅降级**：`torch`/`sentence-transformers` 不在生产依赖里，缺失时自动降级到基础融合而不崩（`test_dual_mode.py` 覆盖所有降级路径）——这是**生产级工程素养**，面试官会喜欢。
- **灌库管线加固**：MD5 去重、按 source 替换、embedding 分批 + 429 退避重试（应对 Gemini 免费档每分钟 100 次 / 每天 1000 次限额）、自动截断参考文献尾部降噪。

**短板**：
- BM25 全量载内存，KB 规模上去（>10 万 chunk）会成瓶颈（代码注释自己也标了这个假设）。
- KB 目前只有 ~16 个文档，规模很小（见 §3）。

### 2.3 检索评估体系 + CI 回归门禁 — ⭐ 项目最稀缺、最值钱的部分

**文件**：`rag/eval/{eval_retrieval.py,evaluate.py,retrieval_metrics.py,golden_dataset_en.json,golden_dataset.json,retrieval_baseline.json}`、`rag/tests/test_retrieval_metrics.py`、`.github/workflows/rag-*.yml`

**这是整个项目里最像「成熟 MLE 团队产出」的部分，也是简历主打。** 大多数学生项目的 RAG 是「我搭了个 RAG demo」，而这里有一整套**客观、可复现、可对照实验、带 CI 门禁的评估**。

**两套互补评估**：

1. **离线检索评估** `eval_retrieval.py`（不需 LLM，只需 query embedding）：
   - **golden set**：`golden_dataset_en.json`，**18 道 in-scope + 6 道 abstention 负样本**；qrels 是**文档/source 级**（抗 re-chunk），带分级相关性 `grade ∈ {1,2,3}`。
   - **指标**（`retrieval_metrics.py`，纯函数 + 单测）：`hit_rate@k / recall@k / precision@k / mrr@k / ndcg@k / ap@k`，k ∈ {3,5,10}；外加 abstention 的 `false_retrieval_rate`。
   - **对照实验**：`--variant all`（bm25 / vector / ensemble 三路对比）、`--sweep`（向量权重网格扫描）、`--gate`（CI 回归）。

2. **端到端答案评估** `evaluate.py`（LLM-as-Judge）：
   - 打 `/v1/chat`，用 Gemini（`temperature=0`）对答案打 **relevance / completeness / accuracy**（1–5 归一化），外加 latency、citation_count。

**实打实的实验发现（这些数字直接能进简历）**：

| 检索变体（同一 KB / qrels） | nDCG@10 | 说明 |
|---|---|---|
| 纯 BM25（跨语言：中文问/英文库） | 0.279 | 词法匹配跨语言几乎失效 |
| 纯向量 | 0.986 | 跨语言场景最优 |
| Ensemble 0.5/0.5（旧默认） | 0.822 | **被 BM25 拖累，劣于纯向量** |
| Ensemble 0.8（英文同语言，生产配置） | 0.986 | 同语言下融合 > 纯向量 |

**结论驱动了产品决策**：通过权重扫描，得出「跨语言用纯向量、同语言用 0.8 融合最优」，并据此把生产 `RETRIEVAL_VECTOR_WEIGHT` 定为 0.8。**这就是「用 metrics 驱动工程决策」的教科书案例**——简历和面试都该重点讲。

**CI 回归门禁**（`.github/workflows/`）：
- `rag-ci.yml`：每个 PR 跑 `ruff` + `pytest`（含指标单测），不调外部 API。
- `rag-retrieval-eval.yml`：检索回归门禁，`--gate` 对照 `retrieval_baseline.json` 阈值地板，回归即 fail；nightly + 手动 + 改动 eval/data/retrieval 的 PR 触发。
- `rag-nightly-eval.yml`：答案层 LLM-as-Judge nightly 门禁，回归自动开 issue。

当前观测（18 in-scope，ensemble@0.8 / Supabase）：recall@3/10 = 1.0/1.0、nDCG@10 = 0.922、MRR@10 = 0.907、FRR = 0.0。

**重要的诚实点（这恰恰能体现成熟度）**：
- KB 只有 ~16 文档，**recall 已饱和到 1.0**，区分度低；项目自己也意识到了，所以头条指标用 nDCG@10 / MRR 而非 recall。面试时主动说出这个 limitation，比假装数字完美更能体现你懂评估。
- abstention 的 `false_retrieval_rate` 在 base ensemble 下因无可比分数返回 -1（不适用），真正的「弃答」评估应在生成层做（项目自己标为 P2 待办）。

### 2.4 视觉识别（拍照识别饭菜）

**文件**：`web/app/actions/parseFoodFromPhoto.ts`、`web/lib/ai/gemini-client.ts`、`web/components/log-form/meal-photo-upload.tsx`

**做了什么**：用 Gemini 原生 SDK（`@google/generative-ai`，强制 JSON 输出）做**图生结构化**：上传饭菜照片 → 输出 `food_name` + 宏量营养素 + `confidence(0–1)` + `notes`。带 **human-in-the-loop**：`confidence ≥ 0.75` 自动保存，否则弹确认框。

**亮点**：有置信度门控 + 人在回路，是负责任的 AI 产品设计。
**短板（纯 MLE 视角）**：本质是**单次 API 调用 + prompt**，没有自训模型、没有分量估计基准、置信度未做校准（calibration）。是「AI 应用」而非「ML 工程」。

### 2.5 自然语言结构化记录（Quick Log / NLP 抽取）

**文件**：`web/app/actions/quickLog.ts`、`logFood.ts`、`logWorkout.ts`

**做了什么**：用一句自然语言（可能同时含「吃了什么」和「练了什么」）→ 单次 LLM 调用做**多意图分割 + 结构化抽取**（`response_format: json_object`）。prompt 里内嵌了「60kg 成年人热量参考表」做 few-shot 风格的引导。

**短板**：同样是 prompt 工程；热量表写死在 prompt 里，应该接结构化食物数据库（如 USDA FoodData Central）+ 单位归一化。

## 3. 数据与知识库现状

**文件**：`rag/data/`、`rag/data/sources.yaml`

- **规模**：约 16 个知识文档 = 5 个人工策选摘要（`kb_*.txt`，如 ISSN 蛋白质/肌酸立场声明）+ ~10 个自动抓取（`auto_*.txt`，训练量/周期化/补剂等）。
- **数据治理（亮点）**：`sources.yaml` 登记每个源的 license，**只收 CC-BY / 公共领域 / 官方指南**，刻意排除付费/版权源（Examine、MASS、MDPI 等），注释里留了反爬/镜像的处理痕迹。这种**数据合规意识**在学生项目里很罕见，是加分项。
- **抓取管线**：`scripts/fetch_sources.py`（trafilatura + requests UA 回退 + PDF pypdf + 参考文献尾部裁剪）。
- **短板**：规模太小，导致检索指标区分度不足（见 §2.3）。扩库是后续重点。

## 4. 工程与 MLOps 成熟度

| 维度 | 现状 | 评价 |
|------|------|------|
| **测试** | `rag/tests/` 用 StubRagService 做契约/单元测试，不调外部 API；前端有 typecheck/lint | 良好 |
| **CI/CD** | 5 个 GitHub workflow：lint+test、检索回归门禁、答案 nightly 门禁、Supabase 灌库、keepalive | **优秀**（学生项目里罕见的「带评估门禁的 CI」） |
| **缓存** | embedding query 缓存 + 检索缓存，memory/Redis(Upstash) 双后端 | 良好 |
| **配置管理** | `pydantic-settings` 统一管理所有 env knob，接口契约 schema 标 LOCKED | 良好 |
| **部署** | 前端 Vercel、后端 Render（Docker，免费档冷启动 + keepalive ping） | 良好 |
| **可观测性** | 仅 SSE debug 字段 + 控制台 print，无结构化日志 / metrics dashboard / 成本追踪 | **待补**（P2） |
| **实验追踪** | 评估报告落 JSON 文件，无 MLflow/W&B | **待补** |
| **模型训练/微调** | **无**，全部调用托管 API | **最大缺口** |

## 5. 成熟度打分卡（MLE 招聘视角，10 分制）

| 能力维度 | 当前分 | 说明 |
|---|---|---|
| RAG / 检索系统 | **8/10** | hybrid + 双后端 + 权重调优，扎实；扣分在 KB 规模小、无 query rewrite/HyDE |
| 评估 / Evaluation | **8/10** | 检索层评估一流；扣分在 Agent/生成层评估缺失 |
| MLOps / CI | **7/10** | 有评估门禁的 CI 很亮眼；扣分在无线上可观测性、无实验追踪 |
| LLM / Agent 工程 | **6/10** | 2 步 tool-calling 设计干净；扣分在无评估、记忆简单、无 model routing |
| **经典 ML / 建模** | **2/10** | **几乎为零，全是 API 调用，无自训/微调模型** |
| 数据工程 / 治理 | **7/10** | license 合规 + 抓取管线加固是亮点；扣分在规模 |
| 软件工程质量 | **8/10** | 清晰边界、契约锁定、降级处理、测试，整体很专业 |

**加权总评**：作为「**LLM/RAG 应用工程师**」方向，这是一个**强项目（约 8/10）**；作为「**通用 MLE（含建模/训练）**」方向，是**中上（约 6/10）**，主要被「无自训模型」拉低。

## 6. 对申请美国 MLE 实习的直接启示

1. **现在就能用**：以「RAG + Evaluation + MLOps」为主线，这个项目已经能写出 3–4 条有量化指标的强简历 bullet（见 [`04-简历与面试.md`](./04-简历与面试.md)）。
2. **最高性价比的补强**（顺序见开发计划）：
   - ① **给 Agent/生成层补评估闭环**（faithfulness / 工具选择准确率 / groundedness）——延续你已经很强的「评估」主线，最自然。
   - ② **加入至少一个自己训练/微调的模型**——补上唯一的硬缺口「经典 ML / 建模」，让简历从「会调 API」升级到「会训模型」。
   - ③ **线上可观测性 + 成本/延迟分析**——补 MLOps，且能产出「把 P95 延迟降低 X%」「把 token 成本降低 Y%」这类招聘官最爱的 bullet。
3. **面试叙事**：你最该反复讲的故事是 **§2.3 的「权重扫描 → 发现等权融合劣于纯向量 → 数据驱动定 0.8」**，它完整体现了 MLE 的核心能力：提出假设 → 设计实验 → 用指标决策 → 上 CI 防回归。
