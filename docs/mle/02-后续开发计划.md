# FitCore 后续开发计划（面向美国 MLE 实习）

> 目标：把 FitCore 从「一个不错的 RAG 应用」打磨成「能在 MLE 实习面试里讲半小时、每个模块都有量化指标」的旗舰项目。
> 设计原则：**每一个里程碑都必须产出一条带数字的简历 bullet**，并补齐一个 MLE 核心能力。
> 配套：[`01-项目现状分析.md`](./01-项目现状分析.md)、[`03-MLE学习指南.md`](./03-MLE学习指南.md)、[`04-简历与面试.md`](./04-简历与面试.md)。

---

## 0. 怎么读这份计划

- 计划分成 **7 个工作流（Track A–G）**，每个 Track 独立，可并行也可单独做。
- 难度（技术含量，不是时间）标注：🟢 易 / 🟡 中 / 🔴 难。
- 每个任务都给出：**动机 → 具体做什么 → 改哪些文件 → 产出的简历 bullet → 学到的 MLE 技能**。
- 已有的 `rag/eval/P0_PLAN.md` 已经完成了 P0/P1（检索评估闭环 + 扩库 + CI 门禁），本计划是**它的延续与升级**，不重复已做的事。

### 推荐优先级（针对「尽快有强简历 + 补硬缺口」）

```
第 1 优先（延续你最强的评估主线，最自然）
  └─ Track A：Agent / 生成层评估闭环  🟡

第 2 优先（补唯一硬缺口：自己训练/微调模型）
  └─ Track D：训练 / 微调一个自己的模型  🔴   ← 让简历从"调 API"升级为"训模型"

第 3 优先（招聘官最爱的"降本提速"数字）
  └─ Track B：线上可观测性 + 成本/延迟优化  🟡

之后按兴趣补强
  ├─ Track C：检索系统进阶（query rewrite / 重排 / chunking A/B）  🟡
  ├─ Track E：个性化推荐（经典 ML 建模）  🔴
  ├─ Track F：安全 / Guardrails 评估  🟢
  └─ Track G：基础设施升级（实验追踪 / 向量库 / 监控）  🟡
```

> **如果你时间紧，只做两件事**：Track A（评估闭环）+ Track D（微调一个模型）。这两条直接把简历的两个最关键维度（Evaluation 深度 + 真实 ML 建模）拉满。

## Track A — Agent / 生成层评估闭环 🟡 ⭐最高优先

**为什么**：你的**检索层**评估已经一流，但**Agent 和生成层**完全没评估（见现状分析 §2.1/§2.3）。补上它，你就拥有了「检索 + 生成 + Agent」**全链路评估**，这是顶级 RAG 工程师的标志。而且它**延续你已有的评估代码**，上手最快。

### A1. Agent 工具选择准确率评估 🟡

- **动机**：Agent 的 `set_retrieval_params` / `query_knowledge_base` / `get_user_stats` 选得对不对，目前无人知晓。
- **做什么**：
  1. 造一个 golden set（30–50 条），每条标注「用户问题 → 期望调用的工具集合 + 期望的 k 档位」。覆盖 4 种模式：纯知识问、纯个人数据问、混合、闲聊（不该调工具）。
  2. 写一个评估脚本：对每条跑 Agent 的 **Step 1 规划**（拿到 tool_calls），与期望对比，算 **tool-selection accuracy / precision / recall（按工具）**、**k 档位命中率**、**闲聊误触发率（false tool-call rate）**。
  3. 接入 CI（类似现有 `rag-retrieval-eval.yml`，设阈值地板）。
- **改哪里**：新增 `web/lib/ai/eval/`（或在 `rag/eval/` 下做一个跨服务的 harness）；新增 golden set JSON。注意 Agent 在 `web/`（TypeScript），可以写 TS 评估脚本，或把 Step1 的纯规划逻辑抽出来用 Node 跑。
- **简历 bullet**：*"Built a golden-set evaluation for an LLM tool-calling agent (50 cases, 4 intent modes); measured tool-selection accuracy (XX%) and reduced false tool-calls on small-talk from XX% to YY% by prompt iteration; gated in CI."*
- **学到**：LLM agent 评估、混淆矩阵、prompt 迭代的量化验证。

### A2. 答案忠实度 / 接地评估（Faithfulness & Groundedness）🟡

- **动机**：RAG 最致命的问题是**幻觉**（答案编造、不忠于检索内容）。现有 `evaluate.py` 只用 LLM-judge 打 relevance/completeness/accuracy，没有专门的 faithfulness。
- **做什么**：
  1. 引入 **RAGAS** 风格的指标：`faithfulness`（答案的每个陈述是否被检索内容支撑）、`answer_relevancy`、`context_precision`、`context_recall`。可以用 RAGAS 库，也可以自己用 LLM-judge 实现「把答案拆成原子陈述 → 逐条判断是否被 context 支撑」。
  2. 在 golden set 上跑，产出 faithfulness 分数；对照「开/关检索」「不同 k」的 faithfulness 差异。
  3. 加 nightly 门禁。
- **改哪里**：扩展 `rag/eval/evaluate.py` 或新增 `rag/eval/eval_faithfulness.py`；`requirements-dev.txt` 视情况加 `ragas`。
- **简历 bullet**：*"Implemented RAGAS-style faithfulness/groundedness eval for the RAG pipeline; quantified hallucination rate and showed retrieval grounding cut unsupported claims by XX%."*
- **学到**：RAG 评估的核心指标体系、幻觉量化、LLM-as-judge 进阶。

### A3. 弃答 / Abstention 在生成层落地（项目自标的 P2）🟡

- **动机**：现状分析指出，检索层无相似度阈值时永远返回 k 条，真正的「资料不足就弃答」要在生成层评估。
- **做什么**：用 6 条 abstention 负样本 + 新造的「问库外问题」集，评估**当 KB 无相关内容时，模型是否正确说『资料不足』而非编造**。算 abstention precision/recall。可加一个检索分数阈值（低于阈值则提示 LLM 弃答）。
- **改哪里**：`rag/app/services/rag_service.py`（阈值逻辑）、`rag/app/prompts/rag_chat.py`（弃答指令已有，强化）、`rag/eval/`（新评估）。
- **简历 bullet**：*"Added retrieval-score-thresholded abstention; raised correct refusal rate on out-of-scope queries to XX% with negligible in-scope recall loss."*
- **学到**：阈值校准、precision/recall 权衡、安全弃答。

## Track D — 训练 / 微调一个自己的模型 🔴 ⭐补硬缺口

**为什么**：这是当前**唯一的硬缺口**（现状打分卡「经典 ML/建模」只有 2/10）。美国 MLE 实习面试**非常看重「你能不能训练/微调模型」**，纯 API 编排会被归类为「AI 应用工程」而非「ML 工程」。下面给 3 个由易到难的选项，**选一个做透即可**。

### D1（推荐入门）：微调一个轻量「快速记录解析」模型，蒸馏掉 Gemini 🔴

- **动机**：`quickLog.ts` / `logFood.ts` 现在每次都调 Gemini 做 NLP 抽取——**慢、贵、依赖外部 API**。这是一个完美的「**知识蒸馏 / 任务微调**」场景。
- **做什么**：
  1. **造数据**：用现有 Gemini（teacher）对大量合成/真实的「一句话记录」生成结构化 JSON（食物/运动 + 宏量），形成 (input, output) 数据集（几千条）。这叫 **distillation data generation**。
  2. **微调 student 模型**：用 **LoRA/QLoRA** 微调一个小模型（如 `Qwen2.5-0.5B/1.5B-Instruct` 或 `Llama-3.2-1B`）专门做这个抽取任务。工具用 HuggingFace `transformers` + `peft` + `trl`（SFTTrainer），可在 Colab/Kaggle 免费 GPU 上跑。
  3. **评估**：在 held-out 测试集上算 **JSON 合法率 / 字段抽取准确率 / 数值 MAE（热量、蛋白）**，对比 teacher（Gemini）和 student（你的微调模型）的**准确率 vs 延迟 vs 成本**。
  4. **（可选）部署**：把微调模型用 `vllm` 或 HF `text-generation-inference` 或 ONNX 导出，做成一个 `/parse` 端点，证明你能**serve 自己的模型**。
- **改哪里**：新增 `ml/` 顶层目录（与 web/rag 并列）：`ml/finetune_parser/`（训练脚本、数据生成、eval notebook）。
- **简历 bullet**：*"Distilled a Gemini-based NLP food/workout parser into a fine-tuned 1.5B model (LoRA); matched teacher on field-extraction F1 (0.9X) while cutting p95 latency 5x and per-call cost ~100% (self-hosted)."*
- **学到（全是 MLE 核心）**：数据集构建、LoRA/QLoRA 微调、SFT、知识蒸馏、模型评估、模型服务/量化。**这一条几乎覆盖了 MLE 面试要问的所有"训练侧"技能。**

### D2（进阶）：微调领域 embedding 模型，提升检索 🔴

- **动机**：现在用通用 `gemini-embedding-001`。健身领域的检索可以通过**微调 embedding** 提升。
- **做什么**：用 golden set + 难负样本（hard negatives）构造对比学习数据，用 `sentence-transformers` 的 `MultipleNegativesRankingLoss` 微调一个开源 embedding（如 `bge-base-en`）；在检索 golden set 上对比微调前后的 nDCG@10/MRR。接入现有 `eval_retrieval.py` 做对照。
- **简历 bullet**：*"Fine-tuned a domain embedding model with contrastive learning (hard negatives) and benchmarked against the offline retrieval harness — +X.X nDCG@10 over the base model."*
- **学到**：对比学习、hard-negative mining、embedding 微调、检索评估对照。

### D3（最硬）：自训一个饭菜图像分类/分量估计模型 🔴

- **动机**：`parseFoodFromPhoto` 现在是 Gemini 单次调用。可以训练一个**真正的 CV 模型**。
- **做什么**：用公开食物数据集（Food-101、Nutrition5k）微调一个图像分类（`timm` 的 ResNet/EfficientNet/ViT）或分量回归模型；评估 top-1/top-5 准确率、分量 MAE；与 Gemini 对比。
- **简历 bullet**：*"Trained a food-image classifier (EfficientNet, fine-tuned on Food-101) reaching XX% top-1; compared against a VLM baseline on accuracy/latency/cost."*
- **学到**：CV 迁移学习、数据增强、图像模型评估。

> **强烈建议从 D1 入手**：它和项目现有功能无缝衔接（快速记录），数据可以用 Gemini 自动造，免费 GPU 够跑，且覆盖最多 MLE 训练技能。

## Track B — 线上可观测性 + 成本/延迟优化 🟡（项目自标的 P2）

**为什么**：招聘官最爱「我把延迟降了 X%、成本降了 Y%」这类 bullet。要拿到这种数字，先得**能测**。

### B1. 结构化请求级日志 + 指标 🟡

- **做什么**：在 `/api/ai/chat` 和 `/v1/retrieve` 加结构化日志（JSON），记录：每请求 latency 分解（规划/检索/生成）、检索命中分数、topK、token 用量（prompt/completion）、模型、mode、是否命中缓存。汇总成简单 dashboard（可用 Grafana + Prometheus，或先落 Supabase 表 + 一个统计页）。
- **改哪里**：`web/app/api/ai/chat/route.ts`、`web/lib/ai/agent.ts`（已有 `latencyMs` 字段，扩展）、`rag/app/api/*`、新增日志模块。
- **简历 bullet**：*"Added request-level observability (latency breakdown, token cost, retrieval hit-scores) across the RAG stack; surfaced that generation was XX% of p95 latency."*

### B2. 延迟 / 成本优化（有了 B1 的数据再做）🟡

- **做什么**：基于 B1 的数据做优化并量化：
  - **Model routing**：规划/解析用更小更快的模型，合成用强模型（现在到处都是 `gemini-2.5-flash`）。
  - **语义缓存**：对相似 query 命中缓存（现有 embedding 缓存可扩展）。
  - **流式首 token 优化 / 并行化**（部分已并行）。
  - 若做了 Track D1 的本地模型，解析路径直接换成自托管模型，成本归零。
- **简历 bullet**：*"Cut p95 chat latency XX% and per-conversation token cost YY% via model routing + semantic caching, validated with before/after observability data."*

## Track C — 检索系统进阶（A/B 对照）🟡

**为什么**：你已有一流的检索评估 harness（`eval_retrieval.py` 支持 `--variant`/`--sweep`/`--gate`），是**做检索实验的天然温床**。每个实验都能直接出对照数字。

### C1. Query 改写 / HyDE / 多查询融合 🟡

- **做什么**：实现并对照 ①query rewriting（LLM 把口语问题改写成检索友好 query）、②HyDE（先让 LLM 生成一个假设答案再 embed 检索）、③multi-query（生成多个 query 取并集）。用 `eval_retrieval.py` 对比 nDCG@10/recall。
- **简历 bullet**：*"A/B-tested query rewriting / HyDE / multi-query against the offline retrieval harness; HyDE improved nDCG@10 by X.X on conversational queries."*

### C2. 重排（reranker）增益量化 🟡

- **做什么**：项目有 CrossEncoder 重排但生产关闭。本地用 GPU 跑 `RERANKER_ENABLED=true python eval/eval_retrieval.py`，量化**重排带来的 nDCG 增益 vs 延迟/内存代价**，给出「值不值得上生产」的结论。
- **简历 bullet**：*"Quantified CrossEncoder reranking: +X.X nDCG@10 at +YY ms latency; recommended against prod use given marginal gain on saturated small-KB recall."*（注意：诚实地说"在小 KB 上增益有限"反而显成熟。）

### C3. Chunking 策略 / embedding 维度对照（需重灌库，项目标的 P3）🟡

- **做什么**：对照 recursive vs semantic chunking、不同 chunk_size、不同 `EMBEDDING_DIM`（768 vs 1536，Matryoshka）对检索质量与存储/成本的影响。
- **简历 bullet**：*"Ran chunking/embedding-dimension ablations; 768-dim Matryoshka embeddings retained 9X% of full-dim nDCG at half the storage."*

### C4. 扩库提升评估区分度 🟢

- **做什么**：现状 recall 已饱和（KB 太小）。按 `sources.yaml` 流程继续扩 CC-BY 源到 40–60 文档，让指标重新有区分度，所有上面的实验结论才更可信。
- **简历 bullet**：（作为其它实验的基础，本身不单列。）

## Track E — 个性化推荐（经典 ML 建模）🔴

**为什么**：另一个补「经典 ML」的方向，且贴合产品（健身 app 天然需要推荐训练/饮食）。

### E1. 训练计划 / 饮食推荐模型 🔴

- **做什么**：用用户的历史日志（`daily_stats`、`workout_logs`）做一个推荐：可以是 ①基于内容的推荐、②协同过滤（矩阵分解 / `implicit` 库）、③一个学习 TDEE 校正的回归模型（用户实际体重变化 vs 预测热量缺口，做在线校正）。
- **简历 bullet**：*"Built a TDEE self-correction model (gradient-boosted regression on logged weight trend vs calorie balance), reducing calorie-target error MAE by XX% vs the static Mifflin-St Jeor formula."*
- **学到**：特征工程、回归/推荐建模、离线评估（MAE/NDCG）、冷启动处理。

> 注意：这需要**真实用户数据**或合成数据。个人项目可先用合成/模拟数据跑通管线，面试时说明「数据是模拟的，重点是建模与评估方法」。

## Track F — 安全 / Guardrails 评估 🟢

**为什么**：健身/营养建议涉及健康，**安全是 MLE 在 LLM 产品里的必答题**，且实现成本低。

- **做什么**：
  1. 加医疗免责声明 + 拒答策略（如「受伤后该怎么练」应建议就医）。
  2. 造一个 red-team 测试集（危险减肥、过量补剂、医疗问题），评估模型的**拒答率 / 安全响应率**，接入 CI。
- **简历 bullet**：*"Built a safety eval (40 red-team prompts on medical/extreme-diet advice); raised safe-refusal rate to XX% via system-prompt guardrails, gated in CI."*

---

## Track G — 基础设施升级 🟡

- **G1 实验追踪**：把评估报告从 JSON 文件升级到 **MLflow / Weights & Biases**，记录每次实验的配置 + 指标，能画趋势图。简历可写「set up experiment tracking」。
- **G2 向量库可扩展性**：把内存 BM25 换成持久化稀疏索引（如 Elasticsearch / OpenSearch / `bm25s`），解决「全量载内存」假设。
- **G3 监控告警**：B1 的 dashboard 加告警（延迟/错误率/成本异常）。

## 综合建议：一条「最大化简历回报」的路线

如果按「投入产出比」排，建议这样推进（每完成一个就更新简历）：

1. **Track A1 + A2**（Agent + faithfulness 评估）→ 拿下「全链路评估」叙事。🟡
2. **Track D1**（蒸馏微调解析模型）→ 补上「训练模型」硬缺口，且能讲延迟/成本。🔴
3. **Track B1 + B2**（可观测性 + 优化）→ 拿下「降本提速」数字。🟡
4. **Track C1 或 C2**（检索进阶实验）→ 再加一条对照实验 bullet。🟡
5. 视精力补 E / F / G。

做完 1–3，你的简历就有：**全链路 RAG 评估 + 自训模型（蒸馏） + 可观测性降本提速**——这是一个**非常完整、各维度都有量化指标**的 MLE 实习简历项目。
